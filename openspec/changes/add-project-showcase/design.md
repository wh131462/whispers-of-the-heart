## Context

现有 `/apps` 数据来自前端 `appRegistry`，用于直接运行站内工具；`DistributedApp` 只保存应用名称、更新标识和版本历史；友链虽然具备后台 CRUD，但语义和字段均不适合承载博主作品。作品展示需要独立的可发布资源，同时在 APP 场景下复用应用分发已有的最新版本数据。

## Goals / Non-Goals

**Goals:**

- 建立可后台维护的作品领域模型和公开查询接口。
- 统一展示开源项目、APP、网站和站内工具，并区分上线、推荐和排序状态。
- 允许 APP 作品关联一个应用分发记录，公开结果自动附带最新版本。
- 在不改变博客主结构的前提下增加首页曝光和独立作品页。
- 保持移动端、暗色模式、加载/空/错误状态完整。

**Non-Goals:**

- 不同步第三方平台元数据，不增加外部 API 或依赖。
- 不实现独立详情页、富文本编辑、访问统计和拖拽排序。
- 不迁移或改写 `appRegistry`、友链及应用分发接口。

## Decisions

### 1. 使用独立 `ShowcaseProject` 模型

作品是有生命周期、分类、排序和多种链接的列表资源，因此不放入 `SiteConfig` JSON，也不复用 `FriendLink`。模型包含固定链接字段、字符串数组标签/平台、发布状态、精选标记和排序值，使 DTO 校验及查询保持明确。相比首版引入通用 `ProjectLink` 子表，固定字段覆盖当前入口且后台编辑更简单。

### 2. 作品与应用分发建立可选多对一关系

`distributedAppId` 可为空并使用 `onDelete: SetNull`。一个分发应用只对应一个公开作品，因此该外键设为唯一；删除分发应用不会删除宣传内容。查询通过 `releases` 按 `versionCode` 降序取一条，服务层生成 `latestRelease` 和有效下载地址，避免持久化派生数据。

### 3. 公开与管理员接口分离

公开 `GET /projects` 只返回 `PUBLISHED` 数据，支持 `featured`、`type` 和有上限的 `limit`；管理员 `/admin/projects` 使用 JWT 与 AdminGuard，提供完整 CRUD 和全部状态。所有接口继续使用现有 `ApiResponseDto` 包裹。

### 4. 共享前端领域类型和展示卡片

作品类型放在 Web 的独立 `project-showcase` 类型文件中，公开页和首页复用同一个展示卡片。首页查询 `featured=true&limit=4`，采用一个主卡加次卡的非对称网格；作品页按类型过滤。后台使用受控表单、媒体库选择、状态切换与数值排序。

### 5. 首页精选无数据时不占位

首页作品接口失败或没有精选作品时隐藏整个区域，避免影响文章主流程；独立作品页则明确展示加载、错误和空状态。

## Risks / Trade-offs

- [作品关联的分发应用尚无版本] → 返回 `latestRelease: null`，并回退到手工下载地址或其他 CTA。
- [外链或图片失效] → 后台使用 URL 校验，前台图片失败时回退到类型图标。
- [排序值重复] → 使用 `sortOrder ASC, updatedAt DESC` 提供确定性次序，不要求排序值唯一。
- [新增迁移受现有失败迁移影响] → 提交纯 SQL 迁移并完成 Prisma 校验/生成；若本地数据库仍有 P3009，只明确记录而不修改旧迁移历史。

## Migration Plan

1. 部署包含枚举、作品表、索引和可选外键的数据库迁移。
2. 部署 API 模块；空表下公开列表正常返回空数组。
3. 部署 Web 页面和入口；首页在没有精选数据时保持现状。
4. 管理员新增并上线作品后，内容自动出现在作品页；勾选首页推荐后进入首页。

回滚时先回滚 Web 和 API，再删除新增表与枚举；现有站内工具、应用分发和友链数据不受影响。
