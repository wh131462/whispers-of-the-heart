## Context

P2P 聊天当前通过单个 `chat-chunk` Action 广播字符串分块，发送调用结束即在本地显示消息。协议没有目标 Peer 状态、远端确认、摘要或恢复检查点；分块也未绑定来源 Peer。共享 `useTrysteroRoom` 已能在 Socket.IO 重连后重建 PeerConnection，并提供 DataChannel 就绪集合、缓冲区背压等待和禁止信令回退的 Action 选项，本变更在聊天层复用这些能力。

## Goals / Non-Goals

**Goals:**

- 只有接收端完成字节长度、分块连续性和 SHA-256 校验后，发送端才显示已送达。
- 在大图片和突发发送场景中控制 DataChannel 缓冲量，并在连接恢复后从接收端首个缺失分块继续。
- 多人房间中按目标 Peer 隔离发送状态、接收缓存和送达结果。
- 限制无效协议数据和过期缓存造成的内存占用，确保重复元数据、分块和完成消息幂等。

**Non-Goals:**

- 不把未完成会话持久化到 localStorage，刷新或主动离开房间后不恢复。
- 不增加服务器消息中继、离线消息、历史记录或新的密码学身份认证。
- 不修改 WebRTC 自带的 ordered/reliable DataChannel 与 DTLS 配置。

## Decisions

### 使用五阶段、按 Peer 定向的应用层协议

每条逻辑消息使用 `messageId`，先发送 `chat-metadata`，接收端以 `chat-ack` 返回接受状态和首个缺失分块；发送端发送 `chat-chunk` 后请求 `chat-finalize`；接收端通过 `chat-verification` 返回最终结果。接收中还会周期发送 `chat-progress`。所有 Action 指定目标 Peer，并启用 `requireDataChannel`。

选择该方案是因为发送调用成功只代表进入浏览器缓冲区，无法证明对端已收到。仅增加最后一个 ACK 也不能支持缺块定位和重连恢复。备选的逐块 ACK 会增加大量往返，因此采用周期进度和最终确认。

### 按 UTF-8 字节分块并校验完整摘要

发送前使用 `TextEncoder` 生成字节，按 16 KiB 切分为 Base64，并计算 SHA-256。元数据固定协议版本、字节长度、分块大小、总块数和摘要。接收端拒绝不一致元数据与越界/长度错误分块，只有 `0..totalChunks-1` 全部存在、总字节数一致且摘要匹配时才解码和展示。

相比按 JavaScript 字符位置切分，该方式不会在代理对、emoji 或多字节文本中产生不稳定边界。SHA-256 用于传输完整性，不替代身份认证。

### 发送队列按目标 Peer 维护检查点

一个逻辑消息冻结发送时的目标 Peer 集合，每个目标分别保存状态、重试次数和当前发送任务。发送循环每块前等待共享 Hook 的低水位通知，并再次检查 DataChannel。连接中断时保留内存队列；DataChannel 重新就绪后重发 metadata，接收端返回首个缺失索引，再从该位置续传。重复块不重复累计字节。

多人房间使用“全部目标均校验成功”为已送达；部分目标成功、其余明确失败为部分送达；全部明确失败为失败。发送时尚未在房间中的 Peer 不补发历史消息。

### 接收缓存采用来源复合键和 TTL

接收会话使用 `peerId:messageId` 复合键，元数据冲突直接拒绝。未完成缓存按最后活动时间清理，已验证会话短期保留以响应丢失的 verification，并通过 `delivered` 标记避免重连重试造成重复展示。消息字节数、分块数、标识和用户名长度均设上限。

### UI 保留消息并展示可重试状态

本地消息在进入发送队列后显示“发送中”，根据每个目标的校验结果更新为“已送达”“部分送达”或“发送失败”。失败或部分送达消息保留内容和发送队列，可由用户重试未成功目标。网络重连期间不清空聊天列表，输入框禁用并显示连接恢复状态。

## Risks / Trade-offs

- **[Risk] 发送前计算大图片摘要会有短暂 CPU/内存开销** → 限制消息字节数并使用浏览器原生 Web Crypto。
- **[Risk] 断线期间内存队列增加占用** → 消息图片沿用 5 MiB 文件限制，完成后立即释放发送分块，接收缓存使用 TTL 清理。
- **[Risk] 对端旧版本不识别新 Action，发送端会超时失败** → 使用独立协议版本和有限次数校验查询，UI 明确显示失败而不误报成功。
- **[Risk] SHA-256 只能证明内容一致，不能证明对端身份** → 保留 WebRTC DTLS 安全边界，并在帮助说明中不宣称额外身份认证。

## Migration Plan

前端双方部署新版本后自动使用新 Action；不需要数据迁移。回滚时恢复旧聊天 Hook 与类型/UI 文件即可，共享 Hook 新增能力保持向后兼容。
